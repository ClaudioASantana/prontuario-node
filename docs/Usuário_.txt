O sistema atual é uma aplicação web monolítica baseada em login centralizado com carregamento dinâmico de páginas conforme o perfil do usuário (médico, paciente, administrador de convênio). 2. Problemas Identificados na Arquitetura Atual



2.1 Acoplamento Monolítico

- Carregamento dinâmico de páginas cria lógica condicional espalhada pela aplicação

- Difícil isolar falhas e realizar testes independentes

- Escalabilidade limitada (um servidor para todas as responsabilidades)



2.2 Autenticação Centralizada

- Único ponto de falha para controle de acesso

- Sem isolamento entre contextos de usuário (médico, paciente, convênio)

- Dificuldade em implementar políticas granulares de segurança



2.3 Prontuário como Entidade Monolítica

- Todas as operações de leitura/escrita em um único banco de dados

- Contenção em acesso a dados para múltiplos usuários simultâneos

- Histórico não segregado por tipo de operação (auditoria, backup, recuperação)



2.4 Falta de Isolamento de Dados

- Risco de acesso não autorizado (vulnerabilidades de autorização)

- Sem segregação clara de responsabilidades entre módulos

- Dificuldade em implementar conformidade com regulações (HIPAA, LGPD)

Proposta de Modernização



1. Arquitetura Orientada a Microsserviços



Recomenda-se uma arquitetura baseada em microsserviços com padrão de domínio (DDD), onde cada módulo opera como um serviço independente com sua própria responsabilidade:



`

┌─────────────────────────────────────────────────────────────────┐

│                     API Gateway (BFF - Backend for Frontend)     │

│              Autenticação, Roteamento, Rate Limiting              │

└────┬──────────────┬──────────────┬──────────────┬────────────────┘

     │              │              │              │

     ▼              ▼              ▼              ▼

┌─────────────┐ ┌─────────────┐ ┌──────────────┐ ┌──────────────┐

│   Patient   │ │   Physician │ │ Health Plan  │ │ Medical Record│

│   Service   │ │   Service   │ │   Service    │ │   Service    │

│             │ │             │ │              │ │ (Core Domain)│

│ • Profiles  │ │ • Licensing │ │ • Coverage   │ │ • Records    │

│ • Auth      │ │ • Sessions  │ │ • Auth       │ │ • Access Log │

│ • Prefs     │ │ • Access    │ │ • Fees       │ │ • Audit      │

└──────┬──────┘ └──────┬──────┘ └──────┬───────┘ └──────┬───────┘

       │               │               │                │

       └───────────────┴───────────────┴────────────────┘

              Event Bus / Message Queue (RabbitMQ / Kafka)

`



2. Decomposição em Microsserviços Independentes



2.1 Serviço de Prontuário Médico (Medical Record Service)

Responsabilidades:

- Armazenamento imutável de registros médicos

- Controle centralizado de acesso (RBAC - Role Based Access Control)

- Auditoria completa de leitura e escrita

- Versionamento de registros



Tecnologias sugeridas:

- PostgreSQL com triggers para auditoria automática

- Event sourcing para histórico imutável

- Cache distribuído (Redis) para leitura de alta frequência



API Central:

`

GET    /records/:patient_id       # Listar prontuários

POST   /records/:patient_id       # Adicionar registro

GET    /records/:patient_id/audit # Auditoria

PUT    /records/:record_id/access # Gerenciar permissões

`



---



2.2 Serviço de Pacientes (Patient Service)

Responsabilidades:

- Perfil do paciente e dados pessoais

- Gerenciamento de consentimentos (autorização de acesso a médicos)

- Preferências e configurações

- Dashboard pessoal



Separação clara:

- ❌ NÃO armazena dados médicos clínicos

- ✅ SIM armazena metadados de autorização e acesso



Integração:

`

Patient Service → Medical Record Service (via API)

Paciente autoriza → Médico obtém token para acessar prontuário

`



---



2.3 Serviço de Médicos (Physician Service)

Responsabilidades:

- Cadastro e credenciamento de médicos

- Especialidades e áreas de atuação

- Sessões e autenticação específica

- Associação com pacientes e convênios



Características:

- Suporta logout automático de sessões expiradas

- Rastreamento de login/logout para auditoria

- Integração com CRM para feedback de pacientes



---



2.4 Serviço de Convênios (Health Plan Service)

Responsabilidades:

- Cobertura de procedimentos e medicações

- Autorização pré-preenchida de despesas

- Integração com processos de faturamento

- Relatórios para análise de custos



Isolamento:

- Lê informações do prontuário apenas para validação de cobertura

- Nunca modifica dados clínicos

- Comunica-se via eventos assíncronos



---



2.5 Serviço de Autenticação e Autorização (Auth Service)

Responsabilidades centralizadas:

- Emissão de JWT tokens com roles específicas

- Validação de tokens em todas as requisições

- Gerenciamento de permissões granulares

- Rate limiting por usuário



Implementação sugerida:

- OAuth 2.0 / OpenID Connect

- Tokens JWT com tempo de expiração curto (15-30 min)

- Refresh tokens para renovação segura

3. Padrão de Autenticação e Autorização Distribuído



Antes (monolítico):

`

Usuário → Login Global → Sessão única → Acesso a tudo autorizado

`



Depois (distribuído):

`

Usuário 

  → Auth Service (JWT com roles)

  → API Gateway (valida token + rate limit)

  → Microsserviço específico (valida permissões no contexto do domínio)

`



Tokens estruturados:

`json

{

  "sub": "user_id",

  "role": "physician|patient|plan_admin",

  "organization": "hospital_id",

  "specialties": ["cardiology", "oncology"],

  "exp": 1735689600

}

`



---



4. Fluxo de Acesso a Prontuários (Exemplo Prático)



`

Sequência: Médico acessa prontuário de paciente



1. Médico faz login → Auth Service retorna JWT com role "physician"



2. Médico solicita prontuário:

   GET /api/medical-records/patient/12345

   Authorization: Bearer <JWT>



3. API Gateway:

   ✓ Valida token JWT

   ✓ Verifica expiração

   ✓ Valida rate limit



4. Medical Record Service:

   ✓ Verifica se médico tem permissão (via Patient Service)

   ✓ Valida se paciente autorizou este médico

   ✓ Log de auditoria: "Physician X acessou prontuário do Patient Y"

   → Retorna dados clínicos



5. Resposta é registrada e auditada

`

5. Considerações de Segurança



5.1 Isolamento de Dados

- Segregação por tenant: Cada organização tem instâncias separadas de dados

- Encryption at rest: Todos os prontuários criptografados com chaves gerenciadas (KMS)

- Encryption in transit: TLS 1.3 em todas as comunicações



5.2 Controle de Acesso Granular

`

Permissões por contexto:

- Médico A pode ler prontuário de Paciente X (autorizado)

- Médico B NÃO pode ler mesmo prontuário (não autorizado)

- Convênio C pode acessar APENAS para validação de cobertura

- Admin pode ler com auditoria completa

`



5.3 Auditoria Completa

`

Log estruturado para cada acesso:

{

  "timestamp": "2025-02-12T10:30:00Z",

  "user_id": "physician_123",

  "action": "read_record",

  "patient_id": "patient_456",

  "resource": "diagnoses",

  "status": "success|denied",

  "reason": "Not authorized" (se negado)

}

`



5.4 Conformidade Regulatória

- LGPD: Direito ao esquecimento implementado via soft-delete + eventual hard-delete

- HIPAA: Auditoria completa de acesso, criptografia obrigatória

- Retenção: Políticas de retenção por tipo de registro (3-7 anos dependendo da Lei)

Recomendações para Manutenibilidade, Escalabilidade e Performance



1. Manutenibilidade



1.1 Estrutura de Código

`

medical-record-service/

├── src/

│   ├── domain/           # Entidades e lógica de negócio

│   ├── application/      # Casos de uso (read record, add note)

│   ├── infrastructure/   # Banco de dados, APIs externas

│   ├── presentation/     # Controllers e validação

│   └── shared/           # Utilitários e tipos compartilhados

├── tests/

├── Dockerfile

└── docker-compose.yml

`



1.2 CI/CD Automatizado

- Testes automatizados para cada serviço (unit, integration)

- Deploy independente de cada microsserviço

- Feature flags para rollout gradual

- Rollback automático em caso de falha



1.3 Versionamento de API

`

GET /v1/medical-records/:patient_id     # Versão 1

GET /v2/medical-records/:patient_id     # Versão 2 (com novos campos)

`

2. Escalabilidade



2.1 Escalabilidade Horizontal

- Stateless: Cada instância do serviço pode processar qualquer requisição

- Load balancing: Distribuir requisições entre múltiplas instâncias

- Kubernetes: Orquestração automática de containers com auto-scaling



2.2 Banco de Dados

- Read replicas: Para leitura de prontuários (pacientes, médicos)

- Write-through cache: Redis para operações frequentes

- Sharding: Particionamento por patient_id para distribuição de carga



2.3 Fila de Mensagens

- Operações assíncronas: Envio de notificações, auditoria, relatórios

- Desacoplamento: Serviços não esperam resposta imediata



`

Médico adiciona prescrição

  → Health Plan Service recebe evento assincronamente

  → Valida cobertura em background

  → Notifica resultado via email/SMS

`



---



3. Performance



3.1 Caching Estratégico

`

Nível 1: CDN (Edge caching)

  - Documentos públicos, imagens de exames



Nível 2: Cache de aplicação (Redis)

  - Perfis de pacientes (5 min TTL)

  - Listas de médicos autorizados (10 min TTL)



Nível 3: Cache do banco de dados (QueryCache)

  - Consultas frequentes com expiração automática

`



3.2 Compressão e Otimização

- GZIP: Compressão de respostas HTTP

- Lazy loading: Imagens de exames carregadas sob demanda

- Pagination: Limitar resultados (20-100 registros por página)



3.3 Índices de Banco de Dados

`sql

-- Medical Record Service

CREATE INDEX idx_patient_records ON medical_records(patient_id, created_at DESC);

CREATE INDEX idx_audit_access ON access_audit(patient_id, accessed_by, timestamp DESC);



-- Patient Service

CREATE INDEX idx_patient_doctors ON patient_authorizations(patient_id, doctor_id);

`



3.4 Monitoramento em Tempo Real

- Prometheus + Grafana: Métricas de latência, throughput, erros

- ELK Stack: Logs centralizados com busca full-text

- Jaeger: Rastreamento distribuído entre microsserviços

Conclusão



A modernização proposta transforma a aplicação de um monolito acoplado em uma arquitetura de microsserviços desacoplada, trazendo os seguintes benefícios:



| Segurança | Centralizada, monolítica | Granular, distribuída, auditada |
